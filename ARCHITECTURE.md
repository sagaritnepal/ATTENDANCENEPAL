# System Architecture Guide (v2)
## Mobile + Cloud Attendance Management System

Supersedes the original web-dashboard guide. Employees now punch in/out from a phone; the
web dashboard becomes an admin/HR console over the same cloud backend. ZKTeco K40 devices are
kept as an optional hybrid source for sites that still use fixed biometric terminals.

## 1. Executive Summary

Mobile-first attendance system for organizations from 10 to 10,000+ employees. Employees check
in/out from a React Native app using one or more verification methods (GPS geofence, QR code,
selfie face match, or a fixed ZKTeco biometric terminal). All data lands in a single Supabase
(Postgres) project that provides auth, storage, realtime, and scheduled jobs — no servers to
provision for the core product.

## 2. Technology Stack

- **Mobile app:** React Native (Expo), TypeScript, React Navigation, Expo Camera/Location/Barcode
  Scanner modules.
- **Admin web console:** reuses the existing prototype's dashboard concepts (kept in
  `server.js`/`public/` for now), to be migrated to a thin Next.js app that talks to Supabase
  directly.
- **Cloud backend:** Supabase — Postgres database, Supabase Auth (employee + admin login),
  Supabase Storage (selfie check-in photos), Supabase Realtime (live dashboard feed), Edge
  Functions / `pg_cron` (payroll calculation, scheduled jobs).
- **ZKTeco bridge:** a small standalone Node.js worker (`zkteco-bridge/`) that keeps the original
  TCP/IP polling logic and upserts into the same `attendance_logs` table via the Supabase
  service-role key. Runs on-prem or on a small VM near each device, not inside the phone app —
  it needs raw LAN socket access that a hosted Edge Function can't provide.
- **Distribution:** Expo EAS Build for iOS/Android binaries and OTA updates; Supabase project
  hosted on Supabase Cloud (managed Postgres, backups, and connection pooling included).

## 3. Punch Verification Methods

The mobile app supports four check-in methods, selectable per branch/employee policy:

| Method | How it works | Stored alongside the log |
|---|---|---|
| GPS geofence | App reads device location, compares against the branch's `latitude`/`longitude`/`radius_meters`. Rejected client-side (and re-checked server-side via a Postgres function) if outside radius. | `lat`, `lng`, `accuracy_m` |
| QR code | Each branch/site displays a rotating QR code (short-lived signed token) generated by an Edge Function. Scanning it proves on-site presence. | `qr_token_id` |
| Selfie + face match | Camera capture at punch time, uploaded to Supabase Storage, compared against the employee's enrolled profile photo (via a face-match Edge Function calling a vision API). | `selfie_url`, `match_score` |
| ZKTeco biometric | Existing K40 fingerprint terminals, unchanged from v1, feeding the bridge worker. | `device_id`, `verification_mode` |

All four write to the same `attendance_logs` table with a `method` column, so payroll calculation
doesn't care which method produced a punch.

## 4. Database Schema Overview (Postgres / Supabase)

| Table | Purpose | Key constraints & indexes |
|---|---|---|
| `profiles` | 1:1 with `auth.users`; role (`admin`/`employee`), links to `employees`. | FK to `auth.users(id)`, RLS: a user reads/writes only their own row (admins read all). |
| `employees` | Core HR profile. | Unique `employee_code`, unique `fingerprint_id`, `profile_photo_url` for face match enrollment. |
| `branches` | Physical sites with a geofence center + radius. | `latitude`, `longitude`, `radius_meters`. |
| `devices` | ZKTeco terminal registry (unchanged from v1). | Indexed by `branch_id`, `status`. |
| `shifts` | Fixed/flexible/rotational schedules. | Linked to `department` or `employee_id`. |
| `attendance_logs` | Immutable punch ledger, any method. | Composite unique key `(employee_id, punch_time)` for dedup; indexed on `(employee_id, punch_time)`; `method` enum column. |
| `qr_tokens` | Short-lived signed tokens per branch for QR check-in. | Unique `token`, `expires_at`, indexed on `branch_id`. |
| `payroll_summaries` | Materialized daily results from the calculation job (late/early/overtime/total hours). | Composite unique key `(employee_id, work_date)`. |

Row Level Security (RLS) is on for every table: employees can only read/insert their own
`attendance_logs`; admins (role in `profiles`) have full read access. Inserts to
`attendance_logs` are validated by a Postgres trigger that re-checks the geofence radius or QR
token validity server-side, so a modified client can't fake presence.

## 5. Sync & Fault Tolerance

- **Mobile punches:** written directly to Supabase via the client SDK. If offline, the app queues
  the punch locally (AsyncStorage) and flushes it on reconnect; the composite unique key on
  `(employee_id, punch_time)` makes retried writes idempotent, same guarantee as v1.
- **ZKTeco bridge:** unchanged polling loop (every 1 minute, exponential backoff on
  unreachable devices), upserting on the same composite key.
- **Realtime dashboard:** admin console subscribes to `attendance_logs` inserts via Supabase
  Realtime (Postgres logical replication under the hood) instead of a custom WebSocket server.

## 6. Payroll & Calculation Engine

Same metrics as v1 (total hours, late/early minutes, overtime), computed by
`compute_payroll_summaries()` — a `plpgsql` port of `calc.js`'s logic, in
`supabase/payroll.sql`. It reads `attendance_logs` + `shifts` and upserts into
`payroll_summaries`, keyed on `(employee_id, work_date)`. Runs on demand
(`select compute_payroll_summaries(current_date);`) or nightly via a `pg_cron` schedule
(commented out at the bottom of `schema.sql` until you've verified it manually).

## 7. Migration Notes from v1

| v1 (web) | v2 (mobile + cloud) |
|---|---|
| Next.js/Express web check-in only | React Native app is the primary check-in surface |
| Custom Express + SQLite | Supabase (Postgres) |
| Socket.io for realtime | Supabase Realtime |
| ZKTeco-only punches | ZKTeco optional, plus GPS/QR/selfie |
| Manual JWT auth | Supabase Auth |
| Redis queue for calc | `pg_cron` / Edge Function |

The relational schema and dedup guarantee carry over unchanged, so `calc.js`'s logic is portable.
